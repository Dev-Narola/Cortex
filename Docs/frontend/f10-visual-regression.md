# Cortex Frontend — F10 Visual Regression

**Status:** F10-Part 3 (Visual Regression Testing) — infrastructure
shipped. The `e2e/visual/` test suite is in place. The **initial
baselines need to be generated by a local workstation run** with
the seeded test fixtures — the Playwright snapshot PNGs are
binary artifacts that don't belong in a code-only delivery.

## Why F10-Part 3 exists

F9 closed the F0–F8 contract on motion, responsive, reduced
motion, keyboard, contrast, and design token discipline. F10-Part 1
established the performance baseline. F10-Part 2 removed the
dead `framer-motion` dep, trimmed the font weight sets, and
fixed the Mono 600 synthesis bug.

**F10-Part 3 is the regression net for the design system itself.**
A future contributor who changes a Button's padding or a Card's
border-radius should fail CI. The F9-P5 `tests/final-qa.test.tsx`
test pins the source-level design contract; F10-Part 3 pins the
**visual** contract.

The roadmap is explicit:

> Visual regression testing (Playwright screenshot diffing or
> Chromatic) — worth adding once the component library is stable
> enough that regressions are actually worth catching automatically,
> not before.

Cortex is now ready: F1 shipped the component library, F9 shipped
the motion/responsive/accessibility pass, and the F0–F8 design
tokens are stable.

## Approach

**Playwright screenshot diffing**, not Chromatic.

- Playwright is already installed (`@playwright/test@1.49.0`)
- Playwright's `expect(page).toHaveScreenshot()` is built-in — no
  separate visual-testing platform
- The existing `playwright.config.ts` is extended with a
  `visual-chromium` project that runs the `e2e/visual/` suite
  with retries disabled (a flaky visual diff is always a real
  diff, not a flake)
- One test file per surface (marketing, auth, app, components)

## Test directory

├── marketing.spec.ts    # marketing surface (light theme)

The `e2e/` (not `tests/visual/`) convention follows the existing
project structure — vitest is in `tests/`, Playwright is in

uses a different structure, keep that structure rather than
creating a parallel convention."

## Determinism contract

The visual baselines must be **reproducible byte-for-byte** on
the same platform. The following are forbidden in any visual
test:

- Real API keys, MCP tokens, passwords, or session JWTs
- Real document contents (use the seeded fixture docs)
- Real email addresses (use the seeded test accounts)
- Real tenant IDs (use the seeded test tenant)
- Random IDs
- Current timestamps (the seeded fixtures use a fixed date)
- Streaming tokens (the chat baseline uses a fully resolved
  assistant message, not a streaming one)
- 3D canvas frames (the 2D fallback is the deterministic
  surface; the 3D canvas is intrinsically non-pixel-stable)

The `prepareForScreenshot` helper enforces the visual
determinism:

- All animations + transitions flattened to 0.01ms (mirroring
  the F9 P3 `prefers-reduced-motion` contract — the baseline
  represents the settled state)
- Network-idle wait before the screenshot
- `document.fonts.ready` wait (the F0 `next/font` setup uses
  `display: swap`, so a screenshot taken before the variable
  font finishes would capture the fallback)
- Theme forced (light for marketing + auth, dark for app)

## Browser matrix

F10-Part 3 keeps the existing 3-browser matrix for the
functional e2e suite (`chromium`, `firefox`, `webkit`) and
adds **one** visual-regression project (`visual-chromium`).
Expanding to Firefox + WebKit visual baselines is a future
expansion — the spec said "start with critical screens, expand
only when useful", and Chromium covers the rendering contract
for the project's Tailwind v4 + OKLCH color system (which is
the same across engines).

The visual project runs serially (`workers: 1`) with
`retries: 0` because a flaky visual diff is always a real
diff, not a flake.

## CI integration

The visual suite is not enabled in CI by F10-Part 3's commit.
The CI integration requires:

1. A deployed environment with the seeded test account
   (`PLAYWRIGHT_VISUAL_TEST_EMAIL` + `PLAYWRIGHT_VISUAL_TEST_PASSWORD`
   env vars)
2. The seeded test fixtures in the backend
3. A baseline-update PR workflow (so intentional UI changes
   don't block other PRs)

The `e2e/visual/README.md` documents the CI YAML fragment
that the project will add when the seeded environment is
ready.

## Pixel-diff tolerance

The default Playwright `maxDiffPixelRatio` threshold (~0.2%)
is used. Screenshots with continuous animation (none in the
current 16-snapshot baseline) would need a looser threshold.
The `snapshot()` helper accepts an optional
`maxDiffPixelRatio` override for future expansion.

## Out of scope (deferred)

- **Firefox + WebKit visual baselines.** Chromium covers
  the rendering contract for the Tailwind v4 + OKLCH
  pipeline. Expanding is mechanical but produces
  platform-specific baseline branches (Playwright
  appends the OS name).
- **CI integration.** Requires the seeded test
  environment to be available to the CI runner. The
  README documents the YAML fragment; the integration
  is deferred until the seed account + fixtures are
  available.
- **Component-level visual regression on every
  primitive's every state.** F10-Part 3 captures the
  default + focus state of the entire F1 showcase as
  one snapshot each. Future expansion: per-component
  snapshots in the visual suite (e.g. Button in
  hover, disabled, loading states; the showcase page
  doesn't currently expose all of these).
- **A/B test-driven visual variants.** That's F10-Part 5.
